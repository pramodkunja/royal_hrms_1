## 2. Phase 4 — role-permission investigation (no code changed; full text `evidence/t98/P4_role_permission_investigation.md`)
**Current web.** Edit Employee role dropdown (`[id]/page.tsx:257-277,684-690`): roles fetched with `page_size=100`; filtered **by name only** (`r.name !== "system_admin"`); a synthetic option for the employee's current role if absent; no `settings.edit` filter on Edit (Add does filter by permission, `AddEmployeeModal.tsx:158`). `role` is always in the save payload. Web's `usePermission` is superuser-or-exact-codename (no `settings.edit` wildcard in the hook); the wildcard reaches web only through the login `is_superuser` flag (= Django flag **or** `settings.edit`, `views.py:612`) and a few explicit `settings.edit` checks (`lib/auth.ts:76`, branches, settings screens). Sidebar uses raw codenames.
**Current Flutter.** Edit dropdown `_RoleSlugDropdown` (`add_employee_sheet.dart:935-989`) filters by name like web Edit, but has **no current-role fallback** (a `system_admin` employee shows an empty field while the slug is still sent) and fetches roles **without `page_size`** (server default 20; web asks 100). Add mode already filters by permission (Task 97). `userHasPermission` treats superuser or `settings.edit` as every codename (`access_control.dart:19-22`) — all employees-feature gates (list edit, FAB, profile edit, promotion, notifier guards) go through it.
**Backend developer's proposed contract (docs 16/17/20 — proposed, not implemented in the backend source today):** remove `settings.edit` from the production `branch_admin` role; refuse granting `settings.edit` to a `can_manage_branch` role; branch-restricted roles get only the codenames they hold (no wildcard); login `is_superuser` true only for real superusers / system roles. All pending product decisions P-1 / P-1b.
**Safe to implement now (Flutter-only, no authorization change; NOT implemented — Phase 4 is investigation-only; ready for approval):**
- D1 — add a display-only fallback item for the employee's current role in the Edit dropdown (and optionally the promotion tab's `_RoleField`) as web does (`page.tsx:684-690`). Risk: low; the value already is sent today.
- D2 — request roles with `page_size=100` for the employees screens (`settings_remote_datasource.dart:494-495`; `rolesProvider` is shared with Settings, so use an employees-only fetch). Risk: low.
**Requires backend confirmation (do not change):** filtering the Edit dropdown by permission; the `settings.edit` wildcard in `userHasPermission`/nav; all-branch pickers for a Branch Admin who holds `settings.edit`; the login `is_superuser` meaning (HO-68a); how the proposed contract changes the wildcard.
**Newly noted — possible live issue (needs backend confirmation):** the server refuses **any** role that holds `settings.edit` on Employee edit **even when the role is unchanged** (`views.py:3612-3613`), and both web and mobile always send `role`. Saving the profile of an employee whose role holds `settings.edit` (the seeded `system_admin`, or a production `branch_admin` that still holds it, HO-18) would therefore return 400 on **both** clients. Added to doc 20 as row 14. Mobile does not work around it; no 403/400 is bypassed.
**Open questions:** P-1 / P-1b decisions; whether the edit refusal should skip an unchanged role; whether the Edit dropdown should adopt web Add's permission filter once the contract lands.
